# 长期维护与闭环开发规范

状态：强制执行  
基线：2026-07-30

本规范约束每一次代码、配置、测试和文档改动。目标不是增加流程表格，而是让每次迭代都有事实依据、可验证结果和防复发证据。

## 1. 唯一事实源

1. 当前源码、可复现行为和自动化测试是实现事实。
2. [README.md](README.md) 索引的需求、架构、测试、Bug 和项目日志是长期事实源。
3. 临时截图、聊天结论、构建目录和本地日志只可作为辅助证据，不得覆盖源码和已编号文档。
4. 同一事实在多份文档中冲突时，必须在当前开发批次内核对源码并同步修正，不把矛盾留给下一次迭代。

## 2. 每次开工

开始改动前必须完成：

1. 阅读 `docs/README.md`、本规范，以及与任务相关的需求、Bug 和测试条目。
2. 检查 `git status`，识别并保留用户已有改动。
3. 检查目标源码、已有测试和最近相关提交，确认现状后再修改。
4. 功能行为关联或新增 `REQ-*`；缺陷关联或新增 `BUG-*`；纯重构在架构文档或项目日志记录目的和不变量。
5. 明确本次验收结果，不以“先搭框架”“以后再补”代替可工作的实现。

## 3. 当次闭环

- 能在当前工作区完成的检查、实现、测试、文档和修复，必须在当前开发批次完成。
- Watch Cloud 的新集成验收直接使用正式 Worker、正式 D1 和正式 OAuth；staging 仅保留为历史证据，不再作为后续发布门禁或验收目标。正式环境中的合成记录必须显式标记、只走产品链路创建/回读/删除，且不得替代传感器精度的户外测试。
- PC、Windows MCP、Tunnel 和手机 8766 不属于生产运行时。后续只验证手机前台/后台/Doze/重启恢复，不再用“三轮 PC-off”作为生产云链路的前置条件。
- 不创建普通 TODO、待办清单、占位实现或无关闭条件的“后续优化”；源码不得新增 `TODO`、`FIXME` 或空 `catch` 来转移问题。
- 修改行为时同步修改需求和测试；修改架构、协议、schema、端口、权限或存储时同步修改架构文档；用户可感知变化同步修改 CHANGELOG。
- 每个有意义的开发批次必须写项目日志，记录目标、实际改动、影响文件、发现的 Bug、根因、修复、防复发测试、验证命令和结果。
- 完成前必须重新检查工作区差异，确保没有调试代码、临时证据、秘密、构建产物或与任务无关的改动进入提交范围。

## 4. Bug 防复发闭环

发现缺陷后按以下顺序处理：

1. 使用稳定 `BUG-*` 编号记录环境、复现步骤、实际结果和预期结果。
2. 先得到最小复现并定位根因，不只修补表面症状。
3. 在当前批次实现修复；同类入口和相同根因一并排查，避免只修一个调用点。
4. 优先增加能在修复前失败、修复后通过的自动化回归测试。受设备、固件或外部服务限制时，增加编号真机/API 用例并记录真实证据。
5. 在 `docs/bugs.md` 记录根因、影响范围、修复位置和验证证据，在 `docs/project-log.md` 记录本次处理过程。
6. 后续出现相同根因时更新原 Bug 并补强原回归门禁，不另建一个没有关联的新编号。

Bug 状态只表示事实：

- `In Progress`：已复现且正在当前批次处理。
- `Fixed`：修复和本地回归已完成，但仍缺明确要求的外部/真机验证。
- `Verified`：规定的自动化及适用真机/API 门禁全部通过，可以转入历史记录。
- `Blocked`：仅限无法由当前工作区解决的外部状态，或需要用户作出会改变结果的决定；必须记录证据、影响和唯一关闭条件。

`Open` 只表示进入本规范前已经确认但尚未进入当前授权范围的历史缺陷，不是愿望型待办。当前批次新发现且在任务范围内可解决的问题不得停在 `Open`；不得用 `Blocked` 代替当前可以完成的工作。只有用户明确要求延期，或已向用户说明真实外部阻断时，才允许留下未闭环项。

## 5. 改动完成门禁

一次开发批次只有同时满足以下条件才算完成：

1. 目标行为已实现，不存在已知的半成品路径。
2. 新发现且可在当前工作区解决的缺陷已经修复。
3. 与改动相称的自动化、契约、模拟器或真机验证已经执行并通过。
4. Bug 修复已有自动化回归；无法自动化时已有编号人工用例和证据。
5. 受影响的需求、架构、测试、Bug、项目日志和 CHANGELOG 已同步。
6. `git diff --check` 通过；纯文档改动还必须通过 Markdown 本地链接检查；代码改动至少通过两个 Android 模块构建。
7. 最终报告列出实际改动、实际执行的命令及结果、产物路径，以及仅由外部条件造成的剩余风险。

发布还必须满足 [testing.md](testing.md) 的发布门禁。开发批次完成不等于允许绕过 P0/P1 发布阻断。

## 6. 允许的例外

以下情况可以暂时不能闭环，但必须显式记录，不得伪装为普通待办：

- 需要尚未提供的真机、账号权限、签名、固件、网络或远端服务状态。
- 需要用户选择会显著改变产品行为、数据兼容或外部系统状态的方案。
- 修复会超出当前授权范围并产生不可逆或高风险外部影响。

例外记录必须包含：已完成的本地工作、阻断证据、当前影响、恢复工作所需的最小条件和条件满足后的验证命令。条件一旦具备，下一次相关迭代优先关闭该项，不重复从头调查。
